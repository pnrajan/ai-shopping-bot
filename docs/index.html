Conversational commerce API with structured product output.

AI Shopping Bot converts a natural-language shopping request into a reply and typed product data in a single HTTP call. It refines earlier results without a new search, builds side-by-side comparisons, and tracks price and availability across catalog providers.

Capabilities

Designed for low latency and predictable cost.

The language model is invoked twice per turn in the standard path. Every other step is deterministic: regular expressions, lookup tables, and cached results are tried before a model call is spent.

Structured query understanding

One model call returns the canonical query, filters, intent, and any specialized intent such as gift mode or an essentials checklist. Downstream stages consume typed fields, never raw text.

In-session refinement

Follow-up constraints such as a price ceiling, brand, or rating are applied to the products already shown. Rule-based filtering handles the common cases; the model is used only when rules cannot decide.

Product comparison

A request of the form "A vs B" runs two targeted searches, selects the best match on each side, and returns a comparison table in the structured payload.

Provider-agnostic model routing

OpenAI, SiliconFlow, and OpenRouter are supported behind one client. Each pipeline role can be assigned a different model through environment variables.

Bounded model usage

A per-request budget caps model calls at four by default. Exceeding it raises an error rather than continuing silently. Call counts are reported in response metadata and asserted in tests.

Operational readiness

API key authentication, per-key rate limiting, SQLite or in-memory sessions, Redis or in-memory caching, OpenTelemetry traces, and a production Dockerfile.

Price and availability tracking

Every product returned by a provider is recorded and folded into a current-state table keyed by provider, product id, and normalized URL. Cached search results are corrected with newer sightings before they are returned. Stale items are refreshed on a schedule, watched items can carry a target price, and changes produce alerts: price drop or rise, back in stock, out of stock, target reached.

Getting started

What you need, and the four commands to a first response.

The default configuration runs entirely offline with a deterministic model stub and catalog. Provider credentials are required only when switching to live mode.

Requirements

  • Required
    Python 3.11, 3.12, or 3.13CI runs the full suite on all three.
  • Required
    GitTo clone the repository. No other build tools.
  • Optional
    DockerA production Dockerfile is included. Mount a volume for SQLite state.
  • Live mode
    One model provider keyOpenAI, SiliconFlow, or OpenRouter. Set SHOPBOT_LLM=live and a model per role.
  • Live mode
    Catalog API keyUnWrangle for a real product catalog. Set SHOPBOT_CATALOG=unwrangle.
  • Scale-out
    RedisShared cache for more than one replica. Optional extra.

Setup

  1. Clone and installCreates a virtual environment, installs dependencies, and copies .env.example to .env.
  2. Start the serverServes on port 8000 and prints mode, tracking store, and log format. Add --dev for auto-reload.
  3. Send a requestUse the request builder on the right, or open the interactive OpenAPI documentation at /docs.
  4. Go live when readyAdd provider keys to .env and switch the mode. Nothing else changes.
git clone https://github.com/pnrajan/ai-shopping-bot.git
cd ai-shopping-bot
bash scripts/setup.sh
bash scripts/run.sh

How it works

An eight-stage pipeline. Any stage can complete the request.

A request context passes through the stages in order. When a stage has produced the answer, the remaining stages are skipped. Persistence always runs. Select a stage for details.

Configuration

Model selection per pipeline role.

Set SHOPBOT_LLM=live and assign a model to each of the four roles. Model identifiers take the form provider/model. Keys are read from the environment, held as secrets, and never logged.

Full environment reference in the deployment guide.

Key settings

VariableDefaultPurpose
SHOPBOT_LLMfakefake runs offline with a deterministic stub. live uses the models above.
SHOPBOT_CATALOGfakefake or unwrangle. Live catalog needs UNWRANGLE_APIKEY.
SHOPBOT_SESSION_STOREmemorymemory or sqlite. SQLite is required for more than one worker.
SHOPBOT_TRACKINGmemoryoff, memory, or sqlite. Price and availability history for every product seen.
SHOPBOT_TRACKING_MONITOR_INTERVAL_S0Re-check watches and refresh stale items on a background loop. 0 means on demand only.
SHOPBOT_LLM_MAX_CALLS_PER_REQUEST4Hard budget per turn. Exceeding it returns 503 rather than continuing.
SHOPBOT_API_KEYunsetWhen set, every endpoint except /health requires X-API-Key.
SHOPBOT_LOG_FORMATtexttext for event key=value lines, json for one object per line. Level via SHOPBOT_LOG_LEVEL.
SHOPBOT_OTEL_ENDPOINTunsetOTLP HTTP endpoint. One span per pipeline stage per turn.

API reference

Endpoints.

All endpoints except /health honor X-API-Key when SHOPBOT_API_KEY is set. Interactive OpenAPI documentation is served at /docs.

MethodPathPurpose
POST/chatConversational turn. Returns reply text plus structured products, a comparison, or clarification questions.
GET/products/searchDirect catalog search with no model call.
GET/products/{provider}/{id}/historyPrice statistics, observation history, and alerts for one product.
GET/tracking/statusTracked item counts by availability, stale count, price range, watches, alerts.
GET/tracking/itemsCurrent state of tracked items. Filter by stock, price range, staleness.
POST/tracking/items/bulkCurrent state for many product ids or URLs in one request.
POST/tracking/refreshRe-check stale tracked items against their providers now.
POST GET DELETE/watchesCreate, list, or remove a watch. A watch may carry a target price.
POST/watches/checkRe-check every watched product now. Returns new alerts.
GET/alertsRecent price and availability alerts.
GET/healthStatus and version.
