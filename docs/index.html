Why it feels fast

Fewer round trips. Clearer contracts.

Every design choice trades an LLM call for a deterministic step wherever one exists.

One call to understand a turn

Canonical query, filters, intent, and specialized intents (gift, essentials checklist, rationale) in a single structured response.

Refinement without re-searching

"Which of these are under $300?" filters the products already shown. Regex first, LLM only if regex misses.

Comparisons

"X vs Y" fetches each product, keeps the best match, and returns a side-by-side table.

Multi-provider routing

OpenAI, SiliconFlow, and OpenRouter behind one client. Pick a model per role and mix freely.

Per-request LLM budget

Default 4 calls. The happy path uses 2. Overruns raise instead of silently continuing.

Pluggable state

In-memory or SQLite sessions. In-memory or Redis cache with 24-hour TTL. API key auth, rate limits, OpenTelemetry, Dockerfile.

How it works

Eight stages. Any one can finish the request.

A request context flows through each stage in order. A stage can mark the request done and the rest are skipped, except persist, which always runs. Click a stage, or let it play.

Quick start

Offline by default. No keys.

A deterministic fake LLM and fake catalog ship in the box, so the full pipeline runs on a laptop with nothing configured.

git clone https://github.com/pnrajan/ai-shopping-bot.git
cd ai-shopping-bot
bash scripts/setup.sh   # creates .venv, installs deps, copies .env.example to .env
bash scripts/run.sh     # serves on http://127.0.0.1:8000

Interactive OpenAPI docs are served at http://localhost:8000/docs once the server is running.

Going live

Mix providers per role.

Set SHOPBOT_LLM=live and choose a model for each of the four roles. Model ids are provider/model. Keys are read from the environment only, held as secrets, and never logged.

For a real catalog set SHOPBOT_CATALOG=unwrangle and UNWRANGLE_APIKEY. Set SHOPBOT_API_KEY to require an X-API-Key header.
